# mochi-oa-server-go × 客户端（mochi-oa）接口一致性分析

> 分析时间：2026-10-13　分析方式：**只读**（未改动客户端 `mochi-oa` 任何代码）
> 服务端：`mochi-oa-server-go`（Go 1:1 复刻）　客户端：`mochi-oa`（Electron + socket.io-client v4）
> 验证工具：`.dsh-workspace/probe-login.mjs`（借用客户端自带 `socket.io-client` 直接跑真实登录）

---

## 一、结论先说

**「无法登录」的根因不是接口不一致，而是 Go 端不建库不建表。**

在全新部署（空 MySQL）下，`users` 等表根本不存在 → 查询失败 → 任何账号都登录不了。
已验证：**鉴权接口本身与客户端完全兼容**（含握手、RSA 加密、ack 形状、推送事件）。

另外原 README 明确写着「不自带建表/迁移 SQL，直接接管老库数据」——这在「换新服务器部署」场景下是致命缺口。

---

## 二、已验证的接口一致性（实测证据）

用客户端自己的 `socket.io-client` 直连 Go 服务端（`STORAGE=memory`，`http://127.0.0.1:3001`）跑完整登录链路：

```
PASS socket.io 连接            {"sid":"e302a46d...","transport":"websocket"}
PASS auth:getPublicKey 返回公钥 {"ok":true,"len":451,"head":"-----BEGIN PUBLIC KEY-----"}
PASS auth:register             {"ok":true}
     rx auth:newDeviceLogin    {"sessionId":41,"device":"dsh-probe",...}
PASS auth:login                {"ok":true,
                                dataKeys:["companies","serverAdmin","session","token","user"],
                                userKeys:["avatar","email","extra","id","nick","phone","username"],
                                hasToken:true}
```

### 兼容性矩阵

| 环节 | 客户端实现 | Go 实现 | 结论 |
|---|---|---|---|
| 传输 | `io(url, {transports:['websocket','polling']})` | `internal/socket`（自实现 EIO4 + socket.io） | ✅ 一致 |
| 握手 auth | `auth: {device}` | 已处理 | ✅ |
| 公钥 | `auth:getPublicKey` → `ack.data.publicKey` | 返回 `{ok, publicKey}`（顶层） | ✅ 客户端 `normalizeAck()` 会把顶层字段自动收进 `data`，兼容 |
| 凭据加密 | `publicEncrypt({padding: RSA_PKCS1_PADDING}, JSON)` → base64 | `base64.StdEncoding` + `rsa.DecryptPKCS1v15` | ✅ 一致 |
| 注册字段 | 加密体 `{username, password}` | 解密后读 `username/password` | ✅ |
| 登录字段 | 加密体 `{account, password}` 或 `{account, code}` | 解密后读 `account/password/code` | ✅ |
| ack 形状 | `{ok, error?, ...rest→data}` | `util.OK(map)` = `{ok:true, ...}` / `util.Fail(msg)` = `{ok:false, error}` | ✅ |
| 登录载荷 | 期望 `token/user/companies`（还有 `session/serverAdmin`） | 返回 `{token,user,companies,session,serverAdmin}` | ✅ |
| 设备推送 | `auth:newDeviceLogin` / `auth:sessionRevoked` | 均有 EmitTo | ✅ |

> ⚠️ 一个**易踩的坑**（我已踩过）：注册接口要求解密后的字段名是 **`username`**，登录要求是 **`account`**。
> 用 `account` 去注册会得到 `注册凭据解密失败`——服务端把「字段缺失」和「解密失败」合并成同一个错误文案，**误导性极强**。

### 客户端连接状态（客户端日志实证）

`%APPDATA%\mochi-oa\logs\renderer-console.log`：

```
07:23:30 [main] [io:lifecycle] connect_error websocket error        ← 服务未启动
07:24:40 [main] state connected=true url=http://127.0.0.1:3001     ← Go 服务起来后立刻连上
07:27:56 [main] state connected=true url=http://127.0.0.1:3001
```

结论：**客户端与服务端的连接层没有问题**，客户端也确实指向了 `3001`。

## 三、任务清单（按你提出的）

### T1　启动时自动建库 + 自动建表　【最高优先级，直接决定能否登录】

现状：README 声明「不自带建表/迁移 SQL，直接接管老库数据」；代码里 `internal/db/mysql*.go`
全是 `SELECT/INSERT ... FROM users/companies/...`，**没有任何 DDL**。

方案：
1. 新增 `internal/db/schema.go`：集中声明 `CREATE DATABASE IF NOT EXISTS` + 全部
   `CREATE TABLE IF NOT EXISTS`（列定义必须与老库 `mochi-oa-server` 的建表口径一致）。
2. 启动流程：连 MySQL（不带 database）→ 建库 → `USE db` → 逐表 `CREATE TABLE IF NOT EXISTS` → 记录每张表的创建/已存在日志。
3. 从老库导出真实 DDL 作为唯一依据（**不要手写猜列**）：
   `mysqldump --no-data --skip-add-drop-table olddb > schema.sql`，再据此生成 Go 常量。
4. 幂等 + 可控：`AUTO_MIGRATE=true|false`（默认 true）；`AUTO_MIGRATE=false` 时只校验表是否存在，
   缺表则**启动失败并明确报出缺哪张表**（而不是让用户登录时才发现）。
5. 提供 `--schema-dump` 之类的子命令，把实际建表语句打印出来便于审计。

### T2　Docker：用 ubuntu 镜像直接跑二进制　【中等】

现状：`docker-compose.yaml` 存在，但需要确认是否走「镜像内构建」而非「直接执行二进制」。

方案：
- `Dockerfile`：`FROM ubuntu:24.04`，只 `COPY mochi-oa-server`（Linux amd64 二进制）+
  `resources/`（如需）→ `ENTRYPOINT ["./mochi-oa-server"]`；不装 Go、不装 Node。
- 交叉编译：`CGO_ENABLED=0 GOOS=linux GOARCH=amd64 go build -trimpath -ldflags="-s -w"`。
- `docker-compose.yaml`：`mysql:8` + `mochi-oa-server`（二进制镜像），
  挂载 `./data:/app/data`、通过 env 传 `MYSQL_*`/`JWT_SECRET`/`STORAGE=mysql`；
  `depends_on: mysql: condition: service_healthy`（healthcheck 用 `mysqladmin ping`）。
- 由于 T1 要做自动建表，容器首次启动即可自举，不再需要人工导入 SQL。

### T3　接口验证脚本（行为以客户端为准）　【高优先级】

已落地：`.dsh-workspace/probe-login.mjs`（登录链路，实测通过）。

待扩展为**全事件覆盖**的验证套件（同样借用客户端自带的 `socket.io-client`，不改客户端）：
- 从客户端源码**自动提取**事件名与载荷字段，生成用例清单，避免"人肉对齐"再次漂移：
  - `src/main/net/server-client.ts`：`emitWithAck(this.socket, '<event>', <payload>)`、`this.emit(...)`、`socket.on('<event>')`
  - `src/preload/index.ts` + `src/main/server-ipc.ts`：IPC → socket 事件的映射
- 对每个事件断言：① 事件名存在；② 载荷字段名一致；③ ack 形状符合 `normalizeAck`；
  ④ 错误文案可区分（见 T5）。
- 输出：`report.json` + 控制台 PASS/FAIL 表。

### T4　服务端详细日志　【中】

现状：299 处 log 调用，但**关键路径缺日志**——例如登录成功/失败**没有任何日志**，
导致排查时只能靠客户端。

方案：给每个 socket 事件统一加进出日志（事件名、sid、userID、耗时、结果），
敏感字段（password/enc/token）脱敏；错误日志带 `event + 入参摘要 + 错误 + 堆栈`。

### T5　消灭「静默吞异常」　【中，但你点名的坏习惯】

扫描结果（54 个 Go 文件）：

| 项 | 数量 |
|---|---|
| `_ = <调用>` 显式丢弃返回值 | **225 处** |
| 含「忽略」字样的注释 | 11 处 |
| `recover()` 兜底 | 4 处（`internal/socket/server.go:246/265/430/439`） |
| `logger./log.` 调用 | 299 处 |

分布 Top：`company.go` 39、`rtc.go` 26、`conversation.go` 24、`group.go` 22、`pm.go` 19。

方案：
1. 建 `logger.Warn/Error` 分级，`_ =` 改为「记日志 + 显式说明为何可忽略」；
2. `recover()` 必须打印堆栈（当前 4 处需逐一确认是否吞栈）；
3. **禁止把不同失败原因合并成同一文案**——本次就吃了这个亏：
   `注册凭据解密失败` 同时覆盖「base64 解不开 / RSA 解不开 / 解开了但缺 username 字段 / JSON 不合法」，
   排查时完全看不出方向。应拆成可区分文案并带最小上下文。

## 六、附：本次分析中我踩过的两个坑（供写验证脚本时注意）

1. **公钥返回是顶层字段**（`{ok, publicKey}`），不是 `{ok, data:{publicKey}}`。
   客户端靠 `normalizeAck()` 兜住了；**验证脚本必须复刻这个归一化**，否则会误判为失败。
2. **注册字段名是 `username`、登录字段名是 `account`**，二者不同；
   用错字段会得到「解密失败」这种误导性错误文案。
